Slicing Chrome's Zucchini patches in half

Chrome's Linux executable is 291 MB. Between two adjacent stable releases, Zucchini — the differ inside Chrome's own updater — produces a 5.9 MB patch. This post introduces a tool that produces a 2.6 MB one for the same pair, byte-for-byte exact: the patch is a structural plan the decoder predicts the new binary from, plus a correction for the bytes it got wrong.

This is a prototype measured on one public release pair, not a change to Chrome's updater.

Why a small change makes a big patch

A one-line source edit rarely produces a one-line byte edit. The change is small, but it is diffuse. Functions slide. A call stores the distance to its target, not the target's address. That distance is its displacement, and it has to be re-encoded whenever the two ends moved by different amounts. Pointers change. A sorted table gains one entry and everything after it slides. Unwind records regenerate. Profile-guided optimisation re-lays-out code nobody touched.

A copy-based differ like xdelta3 handles the slide without difficulty; finding moved regions is what those tools do. What they cannot do is know that the blue bytes are a consequence of the slide. Inside a matched region they are mismatches, and the patch has to carry them. Here that is seven bytes. In Chrome's .text there are 8.7 million such displacement fields, and every one whose two ends moved by different amounts changes.

To ship a binary update, the first thing most people reach for is chunk dedup: split both files into blocks, send only the blocks the old file doesn't have. It is how rsync, casync and content-addressed stores work, and here it sends 88% of the file, because a block survives only if it is byte-identical and a slid function has a changed displacement every few dozen bytes. Granularity is everything.

Both general-purpose differs find the slide at byte granularity, and after that they diverge on what to do about the displacement bytes. xdelta3 copies around them and gets only 6% of the file wrong, yet ships 40 MB, because copying around millions of four-byte holes takes millions of copy instructions, and those are the patch. bsdiff copies through them and is left with 8.7% wrong; those are small differences of large numbers, which is what its diff stream and bzip2 are built for, and the patch is 18.6 MB. Zucchini translates the references inside its copies before it compares, and gets 2.8% wrong plus a list of reference corrections that carry no offsets, so they cannot be placed on the chart above: 5.9 MB. The prediction this post describes is wrong about only 0.6%. The gap between 8.0 MB and 1.8 MB is the relocation table (3.8 MB of Zucchini's, none of presage's), then code (2.6 against 1.2), then .rodata (1.2 against 0.3); in .data.rel.ro both are wrong about the same 20,790 bytes.

Executable differencing has been working on exactly this problem for twenty-five years, and the tools that ended up shipping Chrome updates are the direct descendants of that work:

Baker, Manber and Muth's Exediff (1999) drew the distinction that everything since depends on: primary changes, which come from the edit, and secondary changes, which come from the layout the edit disturbed. Exediff used symbol tables to undo some of the secondary ones, and was tied to one architecture's instruction set.

Colin Percival's bsdiff (2003) was built to be platform-independent, and so understood nothing about the file: it aligned old and new with a suffix array, allowed matches to continue through mismatching bytes, and stored the byte-wise difference of the aligned regions, which is mostly zeros and compresses accordingly. bsdiff's insight was that you do not need to understand a second-order change to encode it cheaply; you only need to line the bytes up so the difference is small. On this Chrome pair that is worth a lot: bsdiff aligns all but 1.9 MB of the new file, and its 18.6 MB patch is 16 MB of diff stream. That stream is the 23.6 million bytes that mismatch inside the aligned regions, almost all of them address fields.

Percival's 2006 thesis is the fuller treatment. It sharpens the taxonomy into zeroth-order changes (timestamps, build ids), first-order changes (the edit itself, proportional to the source diff) and second-order changes (everything the edit induces), quotes the damage — a single modified line can touch 5–10% of the bytes of an executable — and states the problem in one sentence: delta compression of executables is largely the problem of locating and compactly encoding second-order changes.

Google then wrote two differs specifically for shipping Chrome updates. Courgette (2009) did understand the file: disassemble the x86, replace every address with a label, adjust the labels between versions, and diff the label-level representation. On its published example that took a 704 KB bsdiff patch to 79 KB. The price was a decoder whose correctness depended on disassembling and reassembling faithfully, with a fix-up patch for whatever the model got wrong.

Zucchini replaced it in Chrome's updater with a more forgiving design: keep the file as bytes, annotate typed references (relative branches, absolute pointers, relocations), find large equivalent regions between old and new, and translate the references inside them. A missed reference costs a few bytes; it never costs correctness. Zucchini is the baseline for everything that follows.

Presage keeps Zucchini's safety property and pushes the prediction much further. The patch is a compact plan that lets the decoder build a complete, exact-length guess at the new executable from the old one, followed by a correction for every byte the guess got wrong. The guess has to be deterministic. It does not have to be right.

Zucchini, thinly sliced

The chart below starts with Zucchini's method rebuilt inside this framework, then takes one slice off at a time: each layer takes something Zucchini sends as bytes and rebuilds it instead. Each bar is the compressed patch, split into the plan the decoder follows and the correction for what the plan got wrong.

Zucchini's method is three things: an equivalence map (the list of old regions to copy into the new layout, 158,544 of them here, 586 KB compressed); every reference it recognises inside the copies — PC-relative fields in code, absolute pointers in data, the slot address of each relocation entry — translated through that map; and a correction for what is still wrong, one small integer per mistranslated reference and one (offset, byte) pair per wrong byte outside a reference.

The starting point does the same three things with presage's own coder, and lands at 5.1 MB against Zucchini's 5.9. Its equivalence map costs within 30 bytes of Zucchini's. Of the 0.8 MB between them, about half is coding: the same wrong bytes in .rela.dyn and .text cost 640 KB less in presage's correction format. The other half is two streams Zucchini sends that don't pay off on this pair: 200 KB of corrections for the pointer slots the relocations fill, which end up equally right without them, and a 218 KB list of targets with no old counterpart. Presage saves 250 KB elsewhere: .rodata, .eh_frame, the relocation slot addresses, and Zucchini compressing everything as one stream.

Every layer after that is a change to the method, and each has to buy its accuracy for less than it costs to describe. The sections below take the layers in the same order; the small chart under each heading marks which one it covers.

The 26 MB table that isn't bytes

relocation addends as pointers, joined on slot address −1,255,672

This is the first change to Zucchini's method, and the biggest single step in the chart: 1.26 MB.

Chrome's .rela.dyn holds 1,105,993 relative relocations. Each record says "at load time, write this address into that slot". When code and data move, both columns change through the whole table, and a byte-level view of it — including Zucchini's — has almost nothing to copy.

Zucchini treats each entry's slot address as a reference and translates it; the addend it copies as bytes, and its source carries a TODO to handle it. On this table that leaves 1.1 million of 1.1 million addends wrong, 1.77 MB of its patch. The starting point above does the same and pays 1.35 MB. Handling the addend as Zucchini already handles its other references would take its whole patch to 5,263,732, better by 626 KB but still 1.4 MB above the joined layer below.

The obvious fix is to treat the addend as the pointer it is and translate it the way Zucchini translates its other references: old row to new row through the equivalence map. That gets 11% of addends right and costs 1.07 MB, hardly better than the bytes. The moment one relocation slides past another in sort order, every row after it is compared against the wrong entry, and nothing downstream recovers. What works is a join: correct the slot column first, which gives the decoder the exact new slot addresses, then use those slots as keys to match projected old addends to new entries.

Presage regenerates the table column by column: the slot column is a sorted address sequence and is sent as gaps; the addend column is pointers, projected through the address oracle — the decoder’s own answer to "where did the bytes at this old address end up?" — and joined on the rebuilt slots. On Chrome's real table the join takes exact addends from 10.7% of rows to 78.9% with the equivalence map as the only oracle, and the addend column from 1,071,716 compressed bytes to 96,112; once the function map of the next layer resolves the pointers it is 99.19% exact and 15,240 bytes. Across the whole section, sending the table as addresses came out 26× cheaper than correcting the same information as bytes. The entire .rela.dyn plan is 97 KB of the final patch.

One function, three bytes

function map, chosen per function −611,308

Take v8::base::TimeTicks::Now(). Between the two releases it moved 439,328 bytes later in the file. Its body is 98 bytes, and three of them changed:

That is nearly all code churn in a release-to-release build: the same instructions with different addresses inside them. Percival's second-order change, at one instruction. A byte differ pays for it in every one of the roughly 925,000 functions in the image.

The starting point already reproduces those three bytes, most of the time: the equivalences copy the body and the displacement is retargeted through the map. For 139,050 functions — 55 MB of code — it does not, and this layer takes over. It is not that the matcher copied the wrong bytes: nine times in ten the equivalence covering such a function is a single run copied from that function's own old body. What differs is where the displacements inside it end up pointing.

The plan carries a function map. Chrome's publisher has the unstripped build on both sides, so the encoder knows which old function became which new one; the client receives no symbols, only where each matched body came from and where it belongs. The decoder walks each placed function, decodes its x86, and re-encodes every PC-relative displacement — calls, jumps, RIP-relative loads — against the new addresses. For TimeTicks::Now() that reproduces those three bytes from nothing.

The map has to be cheap or it cannot pay. Sent as addresses, the map lists where each old body starts, where it lands, both extents, and the 261,104 points where the oracle needs an exact answer. That costs 1.32 MB compressed, more than the layer saves. Encoded against what the decoder already holds it is 256 KB for the same mappings: function starts as indices into the boundary list the decoder derives from Clang's 0xcc padding, ends inferred from the next start, correspondence points as indices into the set of old branch targets, and each point's shift as the change from the previous one, which is zero 99.2% of the time and turns a 176 KB column into 4 KB. Anything the decoder can enumerate, the plan names rather than spells out.

Even at that price, shipped on its own the map is a step backwards. Retargeting every mapped function through it unconditionally makes the patch 3.94 MB, 122 KB worse than the layer before it: the prediction comes out no better than the equivalences' (98.662% of bytes right against 98.668%) and the map costs 256 KB to send. What makes it pay is one bit per function, choosing whether the equivalence copy or the moved old body is the better starting point. Neither wins everywhere. Equivalences preserve the compiler's local layout, including the islands of data it emits between functions; function identity wins when the byte matcher has grabbed the wrong copy of near-identical code, which identical-code folding (ICF) makes common.

Pointers need one more thing, and this is where the function map pays for itself. A displacement only needs some equivalent destination; a pointer needs the right identity, and ICF means one old address can stand for several logical functions that the new build split apart. Projected through the equivalence map alone, relocation addends come out exact 78.9% of the time; through the function map, with explicit correspondence points for the ambiguous targets, 99.19%, and that column shrinks from 96,112 bytes to 15,240.

Tables the ELF doesn't label

unwind records · rodata jump tables −401,536

.eh_frame is the same problem in a smaller section. Each frame record has a PC-relative start address that moves with its function, and the rest of the record usually doesn't. Retarget the address field through the oracle, keep the record, and .eh_frame_hdr — a sorted index over those records — is regenerated rather than patched as a second copy of the same facts.

.rodata is harder because nothing labels its address tables. Clang's switch jump tables are arrays of 32-bit offsets relative to the table's own base, indistinguishable from any other aligned integers. You can still guess: a run of aligned words that all land inside .text when added to the table base is probably a jump table. That test finds 26,746 candidate tables.

Rewriting all of them made the patch worse. Detection says what a region could be, not whether the rewrite beats the bytes the equivalence layer already supplied. So the encoder tries each candidate against the real target and ships a selection bitmap: 3,559 tables are retargeted, holding 279,412 entries between them, and the rest are left alone. Every later layer works the same way: the model proposes, the encoder measures against the target, and the plan only includes what paid.

Correcting what can't be rebuilt

address-field remap −180,456

After all of the structural layers the decoder has an exact-length prediction that is 99.392% correct. The remaining 0.6% still has shape. Code and data residuals don't want the same encoding: for .text a positional edit list (gap, length, replacement bytes) beat the general matcher; other regions preferred matching. Letting each region pick saved 86 KB for a handful of mode tags. A one-byte opcode fix and a four-byte displacement fix have nothing in common statistically, so bucketing replacement bytes by run length saved another 71 KB, with no signalling at all, because the decoder already knows each run's length.

The last layer went back to addresses. About a quarter of the wrong .text bytes were four-byte displacement fields that resolved to the wrong place. The decoder can enumerate all 8,681,458 such fields in its own prediction. Where many fields disagree about the same target, the plan corrects the mapping once; the stragglers get a signed per-field delta. The encoder rejects any remap that would break more fields than it fixes. This traded 292 KB of plan for 472 KB of correction, and the share of wrong code bytes inside address fields fell from 24.5% to 1.9%.

Where the 2.62 MB goes

Every layer is verified the same way: replay the plan, apply the correction, compare the 291 MB result to the target byte for byte. Rebuilding the image takes 2.3 seconds. A bad structural guess costs bytes, never correctness. For this pair, rebuilding the second-order changes instead of transmitting them cut an already executable-aware patch in half.

What remains is not an address problem. Nearly half of the final patch is .text correction, and 80% of those wrong bytes sit in about 9,000 functions the compiler resized between the two builds. The commit log between the two tags explains the scale: eight bug fixes touching about thirty source files, and six rolls of the Linux PGO profile. Thirty files don't resize 9,000 functions; a new profile does, because it drives inlining and hot/cold splitting across the whole binary. The bytes still to send are mostly the compiler reacting to a profile, not the fixes users are updating for. Predicting that is a different problem from predicting where things landed.
