Patching Go binaries with presage

The first note showed presage halving Chrome's Zucchini patches by having the decoder rebuild the parts of a binary a small change disturbs. Go binaries carry a different kind of disturbance — tens of megabytes of tables the linker regenerates on every build — and one extra layer that understands those tables turns a 3 MB patch into a 74 KB one — and, on the builds most people actually ship, a layer over that turns a 9 MB patch into 335 KB.

What is in a Go binary

A Go program is a statically linked executable with everything it needs inside it: the code, the runtime, and the metadata the runtime uses to run it. That metadata is large. Prometheus 3.13.2 is 94 MB, and less than half of it is machine code.

These tables are what make a Go binary hard to patch. They are not written by hand and not preserved between builds: the linker regenerates them from scratch, sorted by address, packed tightly, with offsets pointing at one another. Add one line to one function and that function grows by a few dozen bytes, every function after it moves, and every table entry that names an address moves with it. The code section changes the way the first note described — every branch that crosses the edit gets a new displacement — and the tables change everywhere. Zucchini finds the moved code well enough; it has no way to know that a 35 MB table is a deterministic function of the function list, so it ships the differences, and a patch release comes out at 3 MB.

There is a tool built for exactly this: go-binsync, a codec written specifically for Go executables and the starting point for this work. It reads the old binary's tables, works out from a short description of the new function list what the new tables must contain, regenerates them, and ships only what it got wrong. On the same pair it produces 74 KB. The question this note answers is whether that kind of format knowledge belongs in a separate tool, or whether it can be one layer of a general predictor — and what happens to patch size when it is.

Presage in one paragraph

A presage patch has two parts. The plan lets the decoder build a complete guess at the new binary from the old one: which functions moved where, which regions are copies of old regions, how references inside them should be translated. The correction lists every byte the guess got wrong. The guess is deterministic, so the encoder can run the decoder's code, see exactly what it will produce, and price the correction before shipping it. Prediction is built from independent layers — whole-file equivalences, a structural function map, reference retargeting, relocation and unwind-table models — each responsible for a kind of region, and each measured by how many bytes it leaves for the correction.

The Go layer

The Go layer is the go-binsync decoder, called as one more layer. Its plan is small: a description of how the new function list differs from the old one (which functions were added, removed or resized), how the data sections shifted, and a few thousand bytes of table content that cannot be derived. From that and the old binary, the decoder regenerates .gopclntab, the type descriptors and the other Go data sections in full, and lays them into the guess. On the patch release above, the layer's plan is about 60 KB compressed and the tables it writes are 47 MB — essentially all of them correct.

Adding the layer changed two other things about how presage works on these files, both worth explaining.

The function map comes for free. Presage's structural layer needs to know which old function became which new one, and where each one now lives. On a Chrome binary that map is built from symbols and transmitted. On a Go binary it is already implied by the Go layer's plan — the function list is the map — so the decoder derives it and the plan carries none. On a small change that is the difference between an 18 KB plan and a 2 KB one.

Code is predicted function by function. The Go layer's model of the code section copies each old function to its new address and retargets its references there. A function that was edited is laid down in pieces — the parts that survived the edit at their new offsets, relocated at their true positions — and the pieces may come from anywhere in the old binary, not just from the function's own old body. That matters more than it sounds: the code a one-line change adds is rarely new to the binary, because the compiler emits the same sequences for the same constructs, and a piece borrowed from the right place is a piece the correction does not have to carry. The encoder tries each candidate by relocating it and keeps it only when the result beats the plain copy by a margin. Presage then chooses, per function, between this model and its own, taking whichever leaves fewer bytes wrong.

Results

Three things to read off the table. Without the Go layer, presage is no better than Zucchini on Go binaries — its Chrome-tuned layers can copy the tables but cannot regenerate them. With it, the shipped codec lands within 0.1 % of the Go-specific tool on every pair, which is the point: the Go transform is now one module of a general predictor, and nothing was lost in the move. The harness column is what the research build gets by choosing, per function, between the Go layer's code model and presage's own — 3 % on the patch release, 6 % on the minor — and that choice is the piece still to port. On the one-line change the plan's fixed streams show: about 300 bytes the single-purpose tool never carried.

The last thousand bytes

At this scale it is worth asking what a patch for a one-line change still contains. Comparing presage's guess against the real file byte by byte: of 30 million bytes, 318 are wrong. 132 of them are random by construction — the build ID the Go linker writes, the GNU build ID, a FIPS integrity hash — and no predictor will ever get them. The remaining 186 are spread over the edited function and a few table entries that refer to it. The rest of the patch is the plan.

What a default build changes

Everything above is for stripped binaries, which is how Go programs are usually shipped. A plain go build also keeps debug information — DWARF — and on the test program that adds 13 MB of it. The sections are compressed with zlib, individually, by the linker. That is a problem for every byte-oriented patcher: the same one-line change that costs 1.2 KB stripped costs 9.3 MB with debug info, for Zucchini and for the Go codec alike, because a compressed stream whose input changed at all is a different stream from beginning to end.

This is the shape of problem presage exists for, and it is handled in two layers. Decompression is exact — Go's own compress/zlib reproduces the linker's output byte for byte at the level the linker uses — so the decoder works on the decompressed bytes and recompresses, shipping nothing for the transform itself. And the section that resists a byte-level delta does so for one structural reason, offsets that slid, which is the same reason code and tables resist it, and is handled the same way: the decoder walks the old .debug_info with the old abbreviation table, finds every reference field, projects its position and its value into the new image — through the run of unchanged bytes that carried it, or a table of paired records where a section is rows that byte-matching aligns by chance — and writes the projected value. Addresses go through the function map the Go layer already has. The same walk covers the address, frame and line tables and the symbol table.

Two things the measurement taught. The equivalence matcher that finds the unchanged runs is worthless on its own — as a whole-file predictor it is 2.5× larger than a plain delta, because a plain delta is the same fuzzy matching with a literal stream — and earns its place only under a layer that fixes what the runs stopped at. And the layer has to be priced: on builds whose debug sections barely changed, the record tables cost more than a positional copy's correction, so the encoder predicts both ways and ships the smaller.

Numbers are from a prototype measured on the pairs shown; the Prometheus binaries are the official release downloads. Zucchini is Chromium's, built from source, with its output compressed by xz -9e as its updater does. Both go-binsync and presage verify their output against the release hash before it is used, so a wrong guess costs bytes, never correctness.

The Go layer and the piece-wise code model are shared code: the changes made while building the layer — deriving the function map, recomputing the ELF headers from the section table, borrowing code from other functions — also shrank the standalone Go codec's patches, from 1,334 to 1,184 bytes on the one-line change and from 1,353,084 to 1,350,486 on the minor release. Since then the codec has become presage itself: go-binsync publishes presage patches, and the Go transform, the decompression transform and the DWARF layer are its modules.
