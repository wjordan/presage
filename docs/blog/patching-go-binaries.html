Patching Go binaries with presage

Prometheus is a 94 MB Go executable. Between two adjacent patch releases, the best general-purpose differs produce patches of 2.7–3 MB. Presage's Go codec produces one of 74 KB — byte-for-byte exact — by having the decoder regenerate the tables the Go linker regenerated.

Presage

Presage is a binary patcher built on one idea: most of the bytes that change between two builds of a program change because something else moved, and a decoder that knows the file format can work those bytes out for itself. A presage patch is a small plan — what moved where — from which the decoder builds a complete prediction of the new file out of the old one, plus a correction listing every byte the prediction got wrong. The prediction is deterministic, so the encoder runs the decoder's code, sees exactly what it will produce, and ships only the difference. Format knowledge lives in codecs: each one claims the files it understands and predicts them, and a file no codec claims falls back to an ordinary delta. Slicing Chrome's Zucchini patches in half shows the approach on a 291 MB C++ binary, where a codec for x86-64 code and ELF tables halves the patch Chrome's own updater ships. This note is about the codec for Go.

What is in a Go binary

A Go program is a statically linked executable with everything it needs inside it: the code, the runtime, and the metadata the runtime uses to run it. That metadata is large. Prometheus 3.13.2 is 94 MB, and less than half of it is machine code.

.gopclntab alone is 35 MB: for every function, a record saying where it starts, which file and line each instruction came from, how deep its stack frame is at each point, and which words on the stack are pointers. .go.type is 12 MB of descriptors the runtime consults for reflection, interfaces and garbage collection. These tables are what make a Go binary hard to patch. They are not written by hand and not preserved between builds: the linker regenerates them from scratch, sorted by address, packed tightly, with offsets pointing at one another. Add one line to one function and that function grows by a few dozen bytes, every function after it moves, and every table entry that names an address moves with it. Every branch that crosses the edit gets a new displacement, and the tables change everywhere. A byte-level differ finds the moved code well enough; it has no way to know that a 35 MB table is a deterministic function of the function list, so it ships the differences.

The Go codec

The Go codec reads the old binary's function table, matches functions between the two builds by name, and works out from a short description of the new function list — which functions were added, removed or resized, and how the data sections shifted — where everything now lives. From that and the old binary the decoder regenerates .gopclntab, the type descriptors and the other Go data sections in full; copies each function to its new address with its PC-relative operands re-targeted; and recomputes the ELF headers from the section table it now knows. A function that was edited is laid down in pieces: the parts that survived the edit at their new offsets, relocated at their true positions, and the pieces may come from anywhere in the old binary — the code a small change adds is rarely new to the file, because the compiler emits the same sequences for the same constructs. The encoder tries each candidate piece by relocating it and keeps it only when the result beats the plain copy.

On this pair the codec's prediction is wrong in 54,520 of 93.8 million bytes. The rest of the patch is the plan and the container. Encoding takes 6 s and applying 1 s; both sides verify the result against the release hash before it is used, so a wrong prediction costs bytes, never correctness. On a 30 MB program rebuilt after adding one if statement — the change that moves 13 % of the file's bytes and nothing else — the patch is 1,201 bytes; bsdiff's is 150,475.

What a default build changes

Everything above is for stripped binaries, which is how Go programs are usually shipped. A plain go build also keeps debug information — DWARF — and for Prometheus that is another 87 MB of it, compressed section by section with zlib by the linker. That is a problem for every byte-oriented patcher: a compressed stream whose input changed anywhere is a different stream from beginning to end, so on the default build the same patch release costs 29 MB whichever tool ships it.

Presage handles it in two layers. Decompression is exact — Go's own compress/zlib reproduces the linker's output byte for byte at the level the linker uses — so the decoder works on the decompressed bytes and recompresses at the end, and the transform itself ships nothing. That alone takes the patch from 29 MB to 8.7 MB, which is what the decompressed debug sections cost as a byte-level delta. The section that resists a byte-level delta, .debug_info, resists it for the same structural reason code and tables do: it holds hundreds of thousands of four-byte references between its own entries, and every one that points past an edited compilation unit shifted by the amount that unit grew. The DWARF layer handles that the same way: the decoder walks the old .debug_info with the old abbreviation table, finds every reference field, projects its position and its value into the new image, and writes the projected value. Positions project through the runs of unchanged bytes around them, or through a table of paired records where a section is fixed-size rows that byte matching aligns by chance; addresses project through the function map the Go codec already has. The same walk covers the address, frame and line tables and the symbol table.

Two things the measurement taught. The matcher that finds the runs of unchanged bytes is worthless on its own: as a whole-file predictor it produces patches 2.5× larger than a plain delta, because a plain delta is the same fuzzy matching with a literal stream, and it earns its place only under a layer that fixes what the runs stop at. And the layer has to be priced: on builds whose debug sections barely changed, the record tables cost more than the correction of a positional copy, so the encoder predicts both ways and ships the smaller. On the 30 MB program with debug information, the one-line change costs 2,002 bytes against 1,201 stripped.
